# MindScreen: Project Report

**Title:** Multimodal Student Mental-Health Screening and Early-Risk Detection Platform: five data categories, one unified pipeline, privacy-preserving workflow

## 1. Research gap
1. Student screening relies on single questionnaires: subjective, biased, a snapshot.
2. ML prototypes often use small or synthetic data, report accuracy only, and judge a student on one average.
3. Few prototypes show a *responsible* path from data to action: consent, access control, audit, aggregate-only researcher views, honest handling of missing data.

## 2. Problem statement
Estimate a student's well-being **screening indicator** from several voluntarily shared, aggregate data categories, show patterns against the student's own baseline, and deliver this in a role-controlled, privacy-preserving workflow, without presenting it as a diagnosis.

## 3. Objectives
1. Collect five categories (screen time, behavioural, physical wellness, social, academic) through separate validated uploads.
2. Store them in one pseudonymous structure; measure completeness; never fill missing values silently.
3. Run **one** unified prediction pipeline (4 models compared) that reports which categories it used and how sufficient the data is.
4. Explain each result (SHAP) and show trends with gaps.
5. Provide consent, deletion, role-based access, audit log and k-anonymised researcher aggregates.

## 4. Input datasets
**A. Training data (real, public):** "Students' Social Media Addiction" survey, 705 students (copy from GitHub `sydneyB6577/Students-Social-Media-Addiction-Dataset` of the Kaggle dataset; **verify author/licence/citation before submission**). Target: self-reported wellbeing score ≤ 5 → at risk (28.7%). Questionnaire-derived and self-reported columns are excluded (`Addicted_Score`, conflicts, relationship status, "affects academics").
**B. Platform input:** five CSV formats (templates in the app). **C. Demo data:** fictional, generated by `src/seed_demo.py`, flagged and kept separate.

## 5. Methodology
```
5 uploads -> validate (columns, ranges, dates, duplicates, consent-gated columns) -> preview -> confirm
          -> cleaned records (SQLite, pseudonymous ID)      [original file stored separately]
          -> unified features (window = last 30/60/90 days) + completeness + quality warnings
          -> model inputs: avg social-media h/day (Screen), avg sleep h (Physical), top app, age, gender, level
          -> 4 models (LR, RF, GB, calibrated SVM) -> estimate + category (Low <35 / Moderate 35-65 / High >65)
          -> SHAP explanation -> stored with model version + timestamp
```
**Why one pipeline, not five models.** The validated model can only use features that exist in its training data (usage and sleep). Behavioural, social and academic data are therefore *collected and shown but not scored*; the interface says so wherever a prediction appears. Adding them to the model requires labelled data (hospital pilot).
**Data sufficiency** (not a statistical confidence interval): Limited < 14 days, Moderate 14-27, Good ≥ 28; downgraded one level when social-media hours were approximated from total screen time. Fewer than 7 days or a missing category → "prediction unavailable".

## 6. Results (public training dataset; held-out 20%, 141 students)

## 7. Privacy and security design
Consent at registration; separate consent for wearable and grade data (withdrawal deletes the stored values); pseudonymous IDs in all record tables; students see only their own data (404 on other users' uploads); researchers see aggregates only with groups < 5 suppressed and cannot open data pages; salted password hashing (Werkzeug scrypt/PBKDF2); CSRF tokens; login rate limiting; strict CSP and security headers; 2 MB CSV-only uploads, server-side validation, spreadsheet-formula neutralisation; originals stored under random names; audit log without PII; self-service data and account deletion; secrets from environment variables.

## 8. Limitations (say these first)
* The model uses screen-time and sleep only; other categories are context. The label is a self-reported score from a small survey, not a diagnosis. Not clinically validated.
* Change monitor (last 7 days vs baseline) is an unvalidated heuristic.
* Calibrated probabilities come from the survey population and may not transfer.
* Demo accounts are fictional. No email verification / password reset; run behind HTTPS for any real use.
* No neurological (EEG) data: no public dataset links it to these behaviours.

## 9. Likely viva questions
* *Why not five models?* Each category is not a separate prediction task; the model can only use features it was trained on. We built one pipeline with explicit "used / not used" reporting.
* *Why do behavioural/social/academic data not change the prediction?* No labelled data links them to outcomes; scoring them would be invented. They feed trends and reports now.
* *How do you avoid false claims?* "Unavailable" states, data-sufficiency label, no accuracy claim for platform predictions, disclaimers on every result.
* *Is the demo real?* Demo records are fictional and labelled; the model and its training data are real.
* *Fairness?* Group metrics are shown to researchers; gaps exist; bias audit is first on the roadmap.
